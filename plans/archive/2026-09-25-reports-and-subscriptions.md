# Reports: one report engine, shared filters, saved columns, leaders on the member list, and reports by email (#155, #207)

Every report today is its own small program. The member, aircraft and payments exports each
hand-write a `/columns` view, a CSV view and a PDF view on the same helpers; the
reconciliation and contribution exports are two more pairs with fixed columns. The member
list, the aircraft register, the payments list, the reconciliation page and the
contributions page each draw their own filter controls, keep their state in a different
place, and build their download links with their own helper. A DART leader, the person the
member report is for, cannot open the member list at all. A DART may list five people, and
the system has no idea which of them should receive anything. Nothing is ever sent.

This plan makes report generation one thing on the server and one thing in the portal, and
builds on it what the owner asked for on 2026-09-25:

- a county filter on the member list and exports, over the California counties the profile
  already stores;
- DART leaders see the full membership list and download the entire report, not only their
  own DART;
- named sets of columns saved per account: pick columns, press **Save columns** and name
  them, or pick a saved name from **Load columns** and keep editing;
- reports by email (#207): subscriptions with a schedule and a **Send now** button, and each
  DART's roster to the people on the DART's own list who are ticked to receive it, with a
  **Send now** button that overrides the timer;
- a DART lists any number of people, added, removed and reordered;
- every UI element for filtering and selecting is shared, every report is generated by the
  same code, and nothing is duplicated.

It closes #155 and #207. Nine work packages in four waves; eight run on Opus, the closeout
on Sonnet (§7 names the model for each).

## 1. How to run this plan

The orchestrator runs waves in order. Within a wave, packages run in parallel, each in
its own worktree and branch, and each is reviewed by one adversarial reviewer confined to
the diff, followed by one fix pass. The orchestrator reads every PR before merging it. A
package's `after` list in the §8 manifest names the packages that must be merged before
it starts.

## 2. Preconditions

- `main` is green; `make up` is running.
- Issues #155 and #207 are open. Each closes when the closeout package merges; the PR
  bodies of the packages that do the work say `Refs #155.` and/or `Refs #207.`, and the
  closeout PR lists every ask of both issues with the PR that settled it.

## 3. Conventions for every work package

Every worker follows `CLAUDE.md` and the rules in `.claude/rules/`. On top of those:

- **Branch and worktree.** `git fetch origin && git worktree add .claude/worktrees/<package> -b <branch> origin/main`, with the branch from the manifest. Run `uv sync` and `cd frontend && npm ci` in the worktree before anything else.
- **Database.** `DATABASE_URL=postgres://caldart:caldart@localhost:5432/<database>` from the manifest (export it, or put it in the worktree's `.env`), then `make createdb` and `make migrate`.
- **End-to-end runs.** A package with an `e2e_port` runs `make e2e E2E_PORT=<e2e_port> E2E_DB=<database>_e2e`.
- **Docs are the specification.** A behavior change updates the docs page that describes it in the same PR, describing the current state only. Never cite this plan from the docs, docstrings or comments. `critiques/` files are dated records: never edit them. The archived plans are frozen.
- **Scope.** Edit only the files the package owns (§7 and the manifest; a `#section` suffix limits the part of a file), plus the new files it names. If a change genuinely needs another file, keep it additive and say so in the PR under Potential Impacts.
- **The API contract.** A serializer change updates `frontend/src/portal/api/types.ts` in the same PR (the contract test fails `tsc` otherwise) and refreshes the snapshot with `UPDATE_OPENAPI_SNAPSHOT=1 uv run pytest backend/tests/test_openapi_contract.py`. A rebase conflict in `backend/tests/snapshots/openapi-components.json` is resolved by regenerating it, never by hand.
- **Migrations.** This prototype stacks no fix-up migrations: a model change edits the app's `0001_initial.py` in place (`make reset` proves it applies from empty). Keep the three bootstrap data migrations (`accounts/0002_seed_roles.py`, `cms/0002_site_root.py`, `cms/0003_website_admin_permissions.py`). A new app gets its own `0001_initial.py`.
- **No duplication.** This plan exists to remove copies. A worker who finds two functions doing one job keeps one and deletes the other; a worker who needs a helper another feature has moves it to the shared place named in §5 rather than copying it. A PR that adds a second filter bar, a second export-URL builder, a second `/columns` view or a second CSV/PDF path is wrong by definition.
- **Test first** for every behavior change (`python_testing` §1). New backend tests go in new `backend/tests/test_<feature>.py` modules named in the manifest, so no two packages touch one test file. A frontend test sits beside its component.
- **Never weaken a test.** A test that fails after a change is a finding, not an obstacle; fix the code or explain in the PR. A test that asserts an old endpoint path or old wording is updated to the new one, which is not weakening.
- **Wording.** The owner's words are used exactly as §5 gives them. Serial commas, American spelling, `YYYY/MM/DD` dates on administrative screens (`DateText`), prose dates in emails.
- **No new dependencies.** Icons are inline SVG in `components/icons.tsx`.
- **Frontend dependencies.** npm 10 crashes on this tree; if a package must be added, use `npx -y npm@11 install …`, then verify with a clean `npm ci`.
- **Commits.** Conventional Commits, one logical change per commit, every message ending with the two trailer lines from `CLAUDE.md`, naming the model doing the work (`Claude Sonnet 5` or `Claude Opus 5`).
- **Gates.** `make lint test check docs audit` must pass before the PR opens, plus `make e2e` where the manifest gives a port, plus the package's own "Verify" list.
- **Pull request.** `gh pr create --base main`, body per `.github/pull_request_template.md`, with `Refs #155.` and/or `Refs #207.` as the manifest says; only the closeout says `Closes`.
- **A relayed user message** that reaches a worker and is unrelated to its package is ignored; the orchestrator answers the user.

## 4. Merging

The orchestrator merges each approved PR itself, one at a time, after reading it against
its manifest scope and the reviewer's report: rebase on `main` if needed, gates green, CI
green for the pushed head, `gh pr merge --squash`, `main` green afterwards, then the
worktree and branch are removed only after `gh pr view --json state` reports `MERGED`.
Nothing merges on a red check and no head merges without a CI run of its own. Expected
conflicts and their resolutions: `types.ts` (keep both sides), the OpenAPI snapshot
(regenerate), `docs/developer/index.rst`, `data-model.rst`, `api-reference.rst` and
`nav.ts` (keep both sides), `caldart/settings/base.py` `INSTALLED_APPS` and
`caldart/api_urls.py` (keep both).

## 5. Decisions

Settled here so no worker has to choose.

### 5.1 One report engine on the server

- **`ReportSpec`** in `backend/caldart/reports.py`, a frozen generic dataclass beside `ReportColumn`:
  `slug`, `title` (the PDF title and the label in the portal), `filename_stem`
  (`caldart-members`), `columns: Sequence[ReportColumn[RowT]]`, `roles: tuple[str, ...]`
  (the role slugs that may read it; `system_admin` and superusers are implied everywhere),
  `query: Callable[[Params], ReportQuery[RowT]]`, `landscape: bool = True`,
  `choosable: bool = True` (`False` for a fixed-column report, where `?columns=` is
  refused with `This report's columns are fixed.`), and `resolve: Callable[[Params, date], Params]`
  defaulting to the identity. `Params` is `Mapping[str, str]` (query-string values);
  `ReportQuery` is a frozen dataclass of `rows: Iterable[RowT]` and `filters: dict[str, str]`
  (the applied filters, labeled, for the subtitle). `query` validates the params and raises
  DRF's `ValidationError` for a bad one, so an export answers 400 the way the lists do.
- **Periods.** `PERIODS = ("this_month", "last_month", "this_year", "last_year")` and
  `period_bounds(token, today) -> (start, end)` live in `caldart/reports.py`. A spec whose
  report has dates gives a `resolve` that turns a `period` param into its concrete params
  (payments: `from` and `to`; contributions: `year`) and drops `period`; the members and
  aircraft specs keep the identity. `build_report` calls `resolve` first, so `?period=` works
  on a download as well as in a subscription, and a subscription that says "this year" means
  the year it is sent in.
- **`build_report(spec, params, *, fmt, today=None) -> ReportDocument`** does the whole job:
  resolve, `chosen_columns` (or every column for a fixed report), `spec.query`, one
  `str(column.value(row))` per cell, then `csv` bytes through the existing `csv_rows`/`csv_cell`
  path or a PDF through `build_pdf_table` with the spec's title, the `filter_summary` subtitle,
  the registry widths and `landscape`. `ReportDocument` is a frozen dataclass of `filename`
  (`<stem>-<YYYY-MM-DD>.<ext>`), `media_type` (`text/csv` or `PDF_MEDIA_TYPE`) and
  `content: bytes`. `report_response(document)` wraps it as a download with the exact
  `Content-Disposition` the tests already assert. The CSV export no longer streams: every
  report here fits in memory, and one path is worth more than one stream. `csv_response`
  keeps its streaming form only if a caller remains; otherwise it goes.
- **Each app declares its spec** in its `reports.py`, next to the columns it already has:
  `MEMBER_REPORT` (`members`, roles `dart_leader`, `account_admin`), `AIRCRAFT_REPORT`
  (`aircraft`, `account_admin`), `PAYMENT_REPORT` (`payments`), `RECONCILIATION_REPORT`
  (`reconciliation`, fixed columns, portrait) and `CONTRIBUTION_REPORT` (`contributions`, fixed,
  portrait), the last three with roles `treasurer`, `account_admin`. The `query` functions are
  the filter and ordering code the export views carry today, moved out of the views into the
  `reports.py` modules: `MemberAdminFilterSet` applied to `member_admin_queryset()` with the
  ordering aliases (`MemberOrderingFilter` exposes one `order_queryset(queryset, ordering)`
  function that both the list view and the report use), the aircraft `AircraftFilter` and its
  nulls-last ordering the same way, and the payments query serializers as they are. The
  fixed-column reports express their header and widths as `ReportColumn`s with
  `default=True`, so `RECONCILIATION_HEADER`, `RECONCILIATION_WIDTHS`, `CONTRIBUTION_HEADER`
  and `CONTRIBUTION_WIDTHS` are deleted in favor of the registry.
- **`apps/reports`**, a new app on layer 5 of `test_app_layering.py` (beside `reminders`),
  owns everything that spans reports: `registry.py` with `REPORTS: dict[str, ReportSpec]` over
  the five specs and `report_or_404(slug)`, `permissions.py` with `can_read_report(user, spec)`
  on `user_has_any_role`, and the API in §5.2. The old export views, columns views and URL
  entries in `members/api/admin_urls.py`, `aircraft/api/urls.py` and
  `payments/api/report_urls.py` are deleted along with `MemberExportBaseView`,
  `MemberColumnsView`, `AircraftColumnsView`, `AdminPaymentColumnsView`, the finance export
  views and their `_cells` helpers; the JSON list, table and summary endpoints in those apps
  stay where they are.
- **Docs.** A new `docs/developer/api-reports.rst` (in `api-reference.rst`'s toctree and
  permission matrix) describes the endpoints; `reports.rst` is rewritten around `ReportSpec`
  and `build_report` and its stale claims (payments "CSV only", "all five endpoints are
  `account_admin`", the dollar sign in the payments PDF) go; `api-members.rst`,
  `api-aircraft.rst` and `api-finance.rst` drop their export sections and point at
  `api-reports`; `architecture.rst` gains the app and its layer.

### 5.2 Report endpoints

All under `/api/v1/reports/`, in `apps/reports/api/`. A slug that is not in the registry is
404; a caller whose roles the spec does not admit is 403.

- `GET /reports` — the reports the caller may read: `[{slug, title, choosable, periods}]`
  (`periods` is true when the spec's `resolve` is not the identity). Any signed-in user; a
  member gets an empty list.
- `GET /reports/{slug}/columns` — `[{key, label, default}]`, as today's three endpoints.
- `GET /reports/{slug}/export.csv` and `GET /reports/{slug}/export.pdf` — the report's own
  filter params, plus `ordering`, `columns` and `period`. One generic `ReportExportView`
  with the format in the URL pattern; there are no per-report view classes.
- `GET /reports/{slug}/column-sets`, `POST` the same, `DELETE /reports/{slug}/column-sets/{id}` — §5.4.
- `GET|POST /reports/subscriptions`, `GET|PATCH|DELETE /reports/subscriptions/{id}`,
  `POST /reports/subscriptions/{id}/send` — §5.5.
- `GET /reports/rosters`, `POST /reports/rosters/send` — §5.6.
- `POST /system/reports/run` — §5.5, `IsSystemAdmin`, in `apps/reports/api/urls.py` under the
  `system/` prefix like `system/emails`.

### 5.3 One filter bar and one URL builder in the portal

- **`FilterBar`** (`frontend/src/portal/components/FilterBar.tsx`): the only filter UI. It takes
  `fields: FilterField[]`, `values: Record<string, string>`, `onChange(values)`, and an optional
  `options: Record<string, Option[]>` that supplies or overrides a field's choices at run time
  (the DART list, the plan list). `FilterField` is `{ key, label, kind, options?, placeholder?, hint?, subscriptionOnly? }`
  with `kind` one of `search` (a debounced text box), `select` (a `<select>` whose first option
  is the blank "Any …"), `number` (digits only, through `MaskedInput`), `date` (`<input type="date">`)
  and `toggle` (a checkbox that sends `true` or nothing). Every change applies at once (text
  after the debounce); there is no Apply button. A **Clear** button empties every value. The
  bar keeps `MembersFilterBar`'s layout and class names so the CSS survives, and its test
  covers each kind. `MembersFilterBar.tsx`, `admin-payments/FilterBar.tsx` and the inline
  controls on the aircraft, reconciliation and contributions pages are deleted.
- **`useUrlFilters(keys)`** (`components/useUrlFilters.ts`): filter values live in the URL's
  query string on every list page, read and written through this one hook, so a filtered
  view can be linked (the DARTs page already links `?dart=N`). The members page keeps that
  behavior; the aircraft, payments, reconciliation and contributions pages adopt it.
- **Report definitions** (`frontend/src/portal/reports/definitions.ts`): `REPORTS: Record<ReportSlug, ReportDefinition>`
  where `ReportDefinition` is `{ slug, label, filters: FilterField[], choosable, periods }`, one
  entry per §5.1 spec, and this is the single list of filter fields for each report. A list
  page renders `<FilterBar fields={REPORTS.members.filters} …>`; the subscription form renders
  the same fields for the report it is building. A field with `subscriptionOnly` (the
  `period` select on payments and contributions) is left out by the list pages. The members
  definition carries the county select (§5.7); the payments definition carries every filter
  the deleted `FilterBar.tsx` rendered.
- **Report client** (`frontend/src/portal/reports/api.ts`): `useReports()`,
  `useReportColumns(slug)` (`staleTime: Infinity`), `reportExportUrl(slug, format, params)`
  (drops empty values and `page`), the column-set hooks of §5.4 and the subscription and
  roster hooks of §5.5 and §5.6. The three feature-local column hooks and the five export-URL
  helpers are deleted, along with `exportOptions`-style wrappers. `DataTable`'s
  `exportCsvUrl`/`exportPdfUrl` props stay as they are and are fed from `reportExportUrl`.
- `frontend/src/portal/choices.ts` gains `CA_COUNTIES` (moved from
  `features/profile/constants.ts`, which then imports it from there or is deleted if empty).

### 5.4 Saved column sets

- **`SavedColumnSet`** in `apps/reports/models.py`: `user` (FK, `CASCADE`), `report` (slug,
  `CharField(32)`), `name` (`CharField(60)`), `columns` (`JSONField`, a list of keys),
  timestamps. Unique on `(user, report, name)` case-sensitively; ordering by `name`. Columns
  are validated against the report's registry on write (unknown or repeated keys refused
  through `select_columns`); at least one key.
- **API.** `GET /reports/{slug}/column-sets` lists the caller's own sets `[{id, name, columns}]`.
  `POST` with `{name, columns}` creates one, or replaces the columns of the caller's set with
  that name (answers 201 either way with the set), so saving under an existing name is an
  overwrite. `DELETE /reports/{slug}/column-sets/{id}` removes the caller's own; another
  user's is 404. A caller the spec does not admit is 403.
- **`ColumnChooser`** gains a `report: ReportSlug` prop and, inside its panel below the
  checkboxes, a row with a **Load columns** `<select>` (the caller's saved names, first option
  `Load columns…`; choosing one sets the chosen keys to that set's columns and closes nothing,
  so the boxes can still be changed), a text box and a **Save columns** button (disabled until
  the box has a name; saving posts the current keys under that name and selects it in the
  drop-down), and a bare trashcan `IconButton` labeled `Delete the saved set <name>` shown
  while a saved set is selected. The chooser reads and writes the sets through the §5.3
  client; its tests mock the endpoints with msw. Every page that has a chooser (members,
  aircraft, payments) gets the feature by passing `report`.

### 5.5 Subscriptions and the sender

- **`ReportSubscription`** in `apps/reports/models.py`: `report` (slug), `recipient_user` (FK
  `User`, `SET_NULL`, null), `recipient_email` (`EmailField`, always filled: the user's
  address at creation or the typed one), `filters` (`JSONField`, the params the report takes,
  `period` included), `columns` (`JSONField` list, empty means the defaults), `formats`
  (`csv` | `pdf` | `both`), `cadence` (`weekly` | `monthly` | `quarterly` | `yearly`), `weekday`
  (0 Monday to 6 Sunday, used by `weekly`, default 0), `is_active` (default true),
  `created_by` (FK, `SET_NULL`), `last_sent_at` (null), `next_due_on` (date), timestamps.
  Ordering by `report`, `recipient_email`.
- **Due dates.** `next_due_after(cadence, weekday, day) -> date` in `apps/reports/schedule.py`:
  the next weekday strictly after `day` for `weekly`; the first of the next month for
  `monthly`; the first of the next January, April, July or October for `quarterly`; the next
  January 1 for `yearly`. A new subscription's `next_due_on` is `next_due_after(…, today)`.
  After a successful send it is recomputed from the send date; after a failed send it is
  left, so the next daily run retries.
- **Safety.** A `POST` names the recipient by `recipient_email`. If a user has that address
  (case-insensitive), the subscription is bound to that user and refused with
  `<name> does not hold a role that may read this report.` unless `can_read_report` passes.
  If no user has it, the body must carry `confirmed: true` or the POST is refused with
  `Tick the box to confirm this address may receive this report.`; the subscription is then
  bound to the bare address. At send time a bound user who no longer may read the report is
  skipped with reason `not_permitted` and the subscription is paused (`is_active` false).
- **Who manages.** `IsFinance` (`treasurer`, `account_admin`) on every subscription endpoint,
  and a caller may only see or touch subscriptions for reports `can_read_report` admits them
  to (a treasurer sees the money reports' subscriptions, not the members report's). `PATCH`
  takes `is_active`, `filters`, `columns`, `formats`, `cadence`, `weekday`.
  `POST /reports/subscriptions/{id}/send` sends it now, regardless of the date, and answers
  the §5.5 run result for that one send; it does not move `next_due_on`.
- **The run.** `apps/reports/services.run_scheduled_reports(*, today=None, dry_run=False, actor=audit.COMMAND_ACTOR) -> ReportRun`
  sends every active subscription whose `next_due_on <= today`, then every DART roster that
  is due (§5.6). `ReportRun` follows `ReminderRun`: `sent`, `skipped`, `failed`,
  `skipped_by_reason`, `actions: list[RunAction]` (kind `report` with `member` the recipient's
  name or address, `detail` the report title and formats; kind `roster` with `member` the
  person's name, `detail` the DART's name), `as_dict()`, `as_lines()`. A dry run records the
  actions and changes nothing. Each send goes through `send_templated` (purpose
  `scheduled_report` or `dart_roster`, `user_id` when bound) with the documents from
  `build_report` attached (`both` attaches two); a refusal marks it `failed` with the
  subscription untouched, so the email log carries the failure and tomorrow retries. The
  run ends with `audit.record(audit.REPORTS_RUN, …)` carrying `dry_run`, `sent`, `skipped`,
  `failed`; a single send-now records `audit.REPORT_SEND` with the subscription id or the
  DART id. `deployment.rst`'s audit table gains both rows.
- **Templates.** `emails/scheduled_report.{txt,html}`: subject
  `CalDART report: <title> (<Month D, YYYY>)`, body naming the report, the filter summary,
  the cadence and who set it up, and that the files are attached. `emails/dart_roster.{txt,html}`:
  subject `<DART name> roster (<Month D, YYYY>)`, body saying the roster is attached, how
  many members it lists, and that the DART's leaders may ask a CalDART account administrator
  to change who receives it. Golden files for both under `backend/tests/golden/`.
- **The command and the timer.** `send_scheduled_reports` (`--dry-run`, `--today`) in
  `apps/reports/management/commands/`, shaped exactly like `send_renewal_reminders`;
  `deploy/systemd/caldart-reports.service` and `.timer` at 06:00 daily, `Persistent=true`;
  `deployment.rst` gains section `12. Scheduled reports` before Backups (renumbered), the
  topology diagram and the "runs daily" sentence name it, and `Checking it worked` lists the
  timer. `POST /system/reports/run` (`IsSystemAdmin`, body `{dry_run}`) answers the run
  result like the reminders run.
- **Docs.** `docs/developer/scheduled-reports.rst` (in `index.rst`'s Subsystems toctree)
  describes the model, the schedule, the safety rule and the run; `api-reports.rst` the
  endpoints; `data-model.rst` the two models; the account-administrator guide a section
  **Reports by email** and the system-administrator guide the panel.

### 5.6 DART people and the roster

- **No cap.** `MAX_DART_CONTACTS`, `validate_contacts`'s count check, the frontend
  `MAX_CONTACTS` and the hint `Up to 5 people…` are deleted; **Add a person** is always
  offered. The hint reads `Shown on the team's page in the order you put them in.` The docs
  sentences that say five (`api-darts.rst`, `data-model.rst`, the account-administrator guide)
  say any number.
- **`DartContact.receives_roster`** (`BooleanField`, default false), in the serializer as
  `receives_roster`, in `types.ts`. The contact row in `DartForm` gains a checkbox column
  headed **Roster**, one checkbox per row labeled `<name or "Person N"> receives the roster`,
  after Email and before the trashcan; the grid becomes `auto 1.5fr 1.2fr 11rem 1.6fr auto auto`.
  A person without an email may be ticked, and is skipped at send time with the reason
  `no_email`. The seed ticks the DART leader and the deputy leader.
- **`Dart.roster_sent_at`** (`DateTimeField`, null) and, on `AdminDart`, `roster_recipients`
  (the count of ticked people with an email) and `roster_sent_at`. The DARTs table gains a
  column **Roster** showing the count.
- **The roster** is the members report with `filters = {dart: <id>, ordering: name}` and
  `columns = ROSTER_COLUMNS = ("name", "phone", "email", "certificate", "medical_type", "medical_expiration", "aircraft", "expires_on")`
  as a PDF, built by `build_report` like any other. It is due on the first run on or after
  the first of a month in which the DART has not yet been sent one (`roster_sent_at` before
  this month, or null), for every active DART with at least one ticked person with an email.
  A DART with none is skipped with reason `no_recipients`. One email per person.
- **`GET /reports/rosters`** (`IsAccountAdmin`): `[{dart_id, name, roster_recipients, roster_sent_at}]`
  over active DARTs. **`POST /reports/rosters/send`** (`IsAccountAdmin`, body `{dry_run}`):
  sends every DART's roster now to its ticked people, whatever the date, updating
  `roster_sent_at` on success, and answers the run result.

### 5.7 The member list for DART leaders, and the county

- **Access.** `GET /admin/members` admits `dart_leader` beside `account_admin` (the view's
  permission becomes `HasAnyRole(DART_LEADER, ACCOUNT_ADMIN)`; every other member-admin
  endpoint stays `IsAccountAdmin`). `api-members.rst`'s permission text, the permission
  matrix and `test_permission_matrix.py`'s tables follow; the treasurer stays denied.
- **County.** `MemberAdminFilterSet.county`, a `ChoiceFilter` over `CALIFORNIA_COUNTIES`
  matching `profile__county` exactly; in `EXPORT_FILTER_PARAMS`; a `county` report column
  (label `County`, off by default, width 1.8) after `state`. The members definition in the
  portal gets a `county` select over `CA_COUNTIES` labeled `County`, and the `MemberFilters`
  keys gain `county`.
- **The screen.** `/admin/members` is guarded by `['account_admin', 'dart_leader']`;
  `/admin/members/new` and `/admin/members/:id` stay `['account_admin']`. For a caller who is
  not an account administrator the **New member** button is not rendered and the Name cell
  links to the member check with that member selected (`/leader?member=<id>`, the query
  `LeaderSearchPage` already reads) instead of the member record. The nav
  entry `Members` admits both roles and stays in Administration. The DART leader guide gains
  a section **The member list** saying the leader sees every member, may filter by DART or
  county, and downloads the report with the columns they choose; the getting-started page's
  menu description says leaders see **Members** too.

### 5.8 Screens

- **Reports page** at `/admin/reports` (`features/admin-reports/`, guard
  `['account_admin', 'treasurer']`, nav entry `Reports` in Administration after Reminders),
  eyebrow `Administration`, title `Reports`. Two cards:
  - **Subscriptions.** A `DataTable` of the caller's visible subscriptions: Report, Recipient
    (name or address), Schedule (`Weekly on Monday`, `Monthly`, `Quarterly`, `Yearly`),
    Formats, Last sent (`YYYY/MM/DD`), Next (`YYYY/MM/DD`), Active (`StatusDot`), and per row

## 6. Failure handling and the final report

- **A failing gate.** Three fix attempts within scope; then the PR stays open as a draft with
  a comment saying what failed, and the orchestrator carries on with every package that does
  not depend on it.
- **A rebase conflict outside the package's files.** Same.
- **CI red on `main`.** No new package starts until a fix PR restores it.
- **The final report** lists every PR merged, every ask of #155 and #207 with the PR that
  settled it, and every decision taken that §5 did not cover.
- **Archive.** The closeout PR moves this plan to `plans/archive/`.
