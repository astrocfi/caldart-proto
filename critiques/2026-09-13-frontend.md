# Frontend critique (2026-09-13)

This report applies the `python-codebase-analysis` skill's ten dimensions and output template (Part 1) and the `critique-test-suite` skill's checklist and report format (Part 2) to `frontend/`, judging both against `.claude/rules/javascript_typescript_best_practices.md` (plus `security.md`, `dependency_management.md` and `environment.md` where they apply) and translating the pytest-specific checklist items to vitest, msw and Playwright.

**Evidence gathered for this report.** `npm run typecheck`: clean. `npm run lint` (`--max-warnings 0`): clean. `npm run test`: 37 files, 393 tests, all passed in 5.16 s; a `--reporter=verbose` rerun printed no React or `act()` warnings. `npm run build`: succeeded; `dist/assets/portal-DyjzE8t5.js` is 498.68 kB (151.75 kB gzip), `site-B4AMRfo6.js` 1.62 kB, `portal-*.css` 46.10 kB, `site-*.css` 34.75 kB, plus about 70 font files. **Not run:** the Playwright specs (they were critiqued by reading them), `npm audit`, and coverage (no vitest coverage provider is installed, so coverage was not measured). All paths below are relative to the repository root unless they start with `src/` or `e2e/`, which are under `frontend/`.

## Part 1: Codebase analysis

**Scope:** `frontend/` — `src/portal/` (SPA), `src/site/` (public-site script), `src/styles/`, the build and lint configuration, and the Django side of the django-vite integration (`backend/templates/portal.html`, `backend/caldart/settings/`). The combined priority list is at the end of the document rather than inside this part.

### Summary

The frontend is in good health: strict TypeScript with `noUncheckedIndexedAccess` is clean, there is no `any`, no `console`, no TODO, only one documented lint suppression, no XSS sink, one central fetch wrapper that handles CSRF, and every portal route guard agrees with the backend permission class behind it. The top priorities are:

1. **The Vite dev-server workflow cannot render the portal.** `portal.html` never emits django-vite's React refresh preamble (high).
2. **Two robustness bugs in the auth and payment paths:**
   - a failed CSRF bootstrap is cached for the life of the page;
   - the route guards treat an `/auth/me` server error as "signed out".
   - A third bug is development-only: `CheckoutReturn` never settles under `<StrictMode>`.
3. **Structural debt against the JS/TS rule:**
   - duplicated hooks and forms;
   - API shapes declared outside `api/types.ts`;
   - roughly half of the exported functions without return types or JSDoc;
   - a single 499 kB bundle with no code splitting.

### 2. Best practices alignment

Measured against `javascript_typescript_best_practices.md`.

- **Strengths.**
  - `src/` has no `export default` (§4) and no `any`, `console` or TODO/FIXME.
  - The single `eslint-disable` carries a rationale (`StripePanel.tsx:136-138`).
  - List keys are stable ids, never array indexes (§10).
  - State updates copy rather than mutate (for example `ProfileForm.tsx:57-68`).
- **Finding (medium)**: Exported signatures do not meet §3 or §7.
  - **Evidence**: A scripted scan of the 219 exported functions in non-test `src/` found 117 without an explicit return type and 136 with no JSDoc block directly above them. Examples:
    - every hook in `src/portal/auth/useAuth.ts:70-132` except `useMe`/`useAuth`;
    - `RequireAuth`, `RequireRole` and `Forbidden` (`src/portal/auth/guards.tsx:33,47,62`);
    - every hook in `src/portal/features/admin-members/api.ts:47-117`.
    - Nothing enforces either rule: `eslint.config.js` has no `explicit-module-boundary-types` and no JSDoc plugin.
  - **Suggestion**: Enable `@typescript-eslint/explicit-module-boundary-types` (and optionally `eslint-plugin-jsdoc`'s `require-jsdoc` for exports), then fix files as they change (rule §2, minimal changes).
- **Finding (medium)**: Errors are swallowed, against §6 ("Do NOT swallow errors").
  - **Evidence**:
    - `ensureCsrfToken` maps both the result and the failure of its fetch to `undefined` (`src/portal/api/client.ts:81-84`); see §7.
    - `parseBody` turns an invalid JSON body into `null` (`client.ts:117-121`), so a 2xx with a broken body resolves as `null` typed as `T`.
  - **Suggestion**: Let a failed bootstrap be retried, and throw a typed error for an unparseable 2xx body.
- **Finding (low)**: Handler names break §1 (`handle*` prefix).
  - **Evidence**: `onKeyDown` (`src/portal/features/checkout/Checkout.tsx:167`), `submit` (`StripePanel.tsx:194`) and `pay` (`MockPanel.tsx:18`), whereas elsewhere the code uses `handleSubmit` (`ProfileForm.tsx:70`).
  - **Suggestion**: Rename them to `handleKeyDown`, `handleSubmit` and `handlePay`.
- **Finding (low)**: Non-null assertions in application code, against §1's explicit null checks.
  - **Evidence**: `Checkout.tsx:165` (`providers[0]!`), `features/leader/AircraftStatusCard.tsx:29` (`VERDICT.none!`), `features/auth/form.tsx:27` (`leftover[0]![1]`).
  - **Suggestion**: Narrow the value explicitly instead.
- **Finding (low)**: Module internals are exported, which §1 says not to do.
  - **Evidence**: `StripePanel.tsx` exports `stripeFor` (:27), `appearanceFromTokens` (:42), `returnUrl` (:75) and `StripeForm` (:180); nothing outside the file imports any of them.
  - **Suggestion**: Un-export them.
- **Finding (low)**: The import style is inconsistent and its documentation is wrong.
  - **Evidence**:
    - `vite.config.ts:16-19` says features import each other as `@/features/<name>`, but the alias maps `@` to `src` (:20-21), so that path does not resolve.
    - The seven files that do use the alias write `@/portal/features/...` (for example `features/join/PayStep.tsx:9`, `features/profile/AircraftEditor.tsx:13-15`).
    - Most other cross-feature imports are relative (`admin-members/api.ts:69`, `leader/api.ts:6`).
  - **Suggestion**: Choose one form and correct the comment.

### 3. Types and static checks

- **Strengths.**
  - `tsconfig.json:18-23` enables `strict`, `noUnusedLocals`/`Parameters`, `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess` and `verbatimModuleSyntax`.
  - `consistent-type-imports` is enforced (`eslint.config.js:29-32`).
  - `src/portal/api/types.ts` matches the backend serializers I compared field by field:
    - `User` (`backend/apps/accounts/api/serializers.py:34-43`);
    - `MemberRow` (`backend/apps/members/api/admin_serializers.py:142-154`);
    - `Payment` (`backend/apps/payments/api/serializers.py:93-107`);
    - `PaymentPeriodSummary` (:122-127);

    - `Aircraft` (`backend/apps/aircraft/api/serializers.py:80-100`);
    - `LeaderSearchResult` (:133-137).
- **Finding (medium)**: API shapes are declared outside `api/types.ts`. This contradicts rule §3 and `CLAUDE.md`'s claim that `types.ts` "already types every object in PLAN §6".
  - **Evidence**:
    - §6.4 member detail: `MemberDetail`, `MemberTerm`, `MemberPayment` and `AdminProfile` live in `src/portal/features/admin-members/types.ts:24-75`. `MemberPayment` (:45-58) re-lists `Payment` (`api/types.ts:209-224`) minus `user_id`/`user_name`.
    - §6.5 aircraft detail: `AircraftDetail` and `AircraftPilot` live in `src/portal/features/aircraft/api.ts:22-39`, and the leader feature reuses them for `/leader/aircraft` (`features/leader/api.ts:6,31`).
    - §6.2: `AdminUserPatch` (`features/admin-users/api.ts:9-15`) and `SendPasswordResetResult` (:71-73).
    - §6.1: `PasswordResetRequestPayload` (`auth/useAuth.ts:25-27`).
    - §6.5: `AttachedAircraft` (`features/profile/api.ts:33-35`).
  - **Suggestion**: Move these into `api/types.ts` (an additive shared-file change), deriving `MemberPayment` as `Omit<Payment, 'user_id' | 'user_name'>`.
- **Finding (medium)**: Response bodies are cast, never checked.
  - **Evidence**:
    - `request<T>` ends with `return body as T` (`client.ts:165`), so every `api.get<T>` is an unchecked cast from `unknown`.
    - `parseBody` returns text for any non-JSON response (`client.ts:123-124`), so an HTML page served with status 200 (a proxy or maintenance page) would arrive as a string typed as `T`.
    - Rule §3 asks for `unknown` narrowed with type guards.
  - **Suggestion**: At minimum, throw a typed error when a 2xx response is not `application/json` (204 excepted). Runtime schemas are optional.
- **Finding (low)**: `CheckoutResponse.client` is not a discriminated union.
  - **Evidence**:
    - It is typed `{ client_secret?: string; order_id?: string }` (`api/types.ts:256-263`). PLAN §6.7 defines one shape per provider (Stripe `{client_secret}`, PayPal `{order_id}`, mock `{}`).
    - Callers re-check at runtime (`StripePanel.tsx:121-125`, `PayPalPanel.tsx:51-52`).
  - **Suggestion**: Make it a discriminated union on `provider` (rule §3).
- **Finding (low)**: Loose `string` fields where unions exist.
  - **Evidence**: `SiteConfig.theme` (`api/types.ts:365`), although `src/site/nav.ts:9-10` defines `Theme`; `Health.db` (`api/types.ts:337`).
  - **Suggestion**: Use the unions.
- **Finding (low)**: Linting is not type-aware.
  - **Evidence**: `eslint.config.js:11` extends `tseslint.configs.recommended`, so `no-floating-promises` and `no-misused-promises` are unavailable to back rule §6 ("Handle rejected promises"). The async `submit` passed to `onSubmit` (`StripePanel.tsx:194,229`) is safe only because it catches internally.
  - **Suggestion**: Adopt `recommendedTypeChecked` for `src/`.
- **Finding (low)**: Test globals leak into production types.
  - **Evidence**: `tsconfig.json:15` adds `vitest/globals` and `@testing-library/jest-dom` to every file, and `vite.config.ts:41` sets `globals: true`. Yet all 37 test files import `describe`/`it`/`expect` from `'vitest'` explicitly, and production code could reference `expect` or `vi` without a type error.
  - **Suggestion**: Drop the globals, or scope them to a test tsconfig.

### 5. Performance and resource use

- **Finding (medium)**: No code splitting.
  - **Evidence**:
    - The build emits one `portal-DyjzE8t5.js` of 498.68 kB (151.75 kB gzip), 1.3 kB under Vite's default 500 kB warning.
    - `src/` contains no `lazy(` and no `import(`; `src/portal/routes/index.tsx:12-24` imports every feature statically.
    - So a member on a phone (PLAN §1) downloads the admin, system and payment-report screens and the Stripe and PayPal React wrappers.
    - Stripe.js and the PayPal SDK themselves load at runtime only when their panel mounts (`StripePanel.tsx:27-33`, `PayPalPanel.tsx:37-39`), which is good.
  - **Suggestion**: Use React Router's `lazy` route property inside each `routes/<feature>.tsx`, which keeps the one-file-per-feature ownership, starting with `admin-*`, `system` and the checkout.
- **Finding (low)**: Every font subset is imported.
  - **Evidence**:
    - `src/styles/index.css:13-20` imports `@fontsource/ibm-plex-*/<weight>.css`, which carries every unicode subset.
    - The build therefore emits Cyrillic, Greek, Vietnamese and Latin-ext faces in woff and woff2, and both CSS bundles hold `@font-face` rules for all of them.
    - Browsers fetch only the subsets a page uses, so the cost is CSS size and build output. i18n is a PLAN §1 non-goal.
  - **Suggestion**: Import the `latin-<weight>.css` entry points.
- **Finding (low)**: One cache invalidation does nothing, and another uses a literal key.
  - **Evidence**:
    - `Checkout.tsx:84` invalidates `['membership']`, a key no query uses: the membership query is `['me','membership']` (`features/profile/api.ts:26`).
    - `Checkout.tsx:83` spells `['auth','me']` rather than `AUTH_ME_KEY` (`auth/useAuth.ts:22`).
    - The refresh that actually works is `refreshAfterPayment` (`features/join/refresh.ts:14-18`), called from `PayStep.tsx:27`, `RenewPage.tsx:32` and `JoinWizard.tsx:54`.
  - **Suggestion**: Keep one owner of post-payment invalidation and delete the other.
- **Finding (low)**: Paginated lists behave inconsistently between pages.
  - **Evidence**: `useAdminPayments` and `useAdminUsers` keep the previous page as placeholder data (`features/admin-payments/api.ts:72`, `features/admin-users/api.ts:47`); `useMembers` (`features/admin-members/api.ts:47-57`) and `useAircraftList` (`features/aircraft/api.ts:75-82`) do not.
  - **Suggestion**: Give the latter two the same `placeholderData`.
- **Finding (low)**: The Stripe panel keeps creating PaymentIntents.
  - **Evidence**:
    - Opening the Stripe tab, and every settled plan or contribution change, posts `/payments/checkout`, which creates a server-side Payment and a PaymentIntent (`StripePanel.tsx:108,113-139`; header comment :6-7).
    - Under `<StrictMode>` (`src/portal/main.tsx:14`) the mount effect runs twice in development. The `cancelled` flag drops the first response, but the first request has already been sent, so each tab open creates two.
  - **Suggestion**: Pass an `AbortSignal` (the client already supports `signal`, `client.ts:97,157`) and consider updating the pending intent instead of replacing it.
- **Strength.**
  - Sensible query defaults: 30 s `staleTime`, no refetch on focus, no retry on 4xx (`src/portal/App.tsx:15-30`).
  - Login and logout empty the cache (`auth/useAuth.ts:84,107`).
  - Query keys include their filters.

### 7. Security and robustness

**Strengths.**
- No XSS sinks: there is no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or `new Function` in `src/` (the one `innerHTML` is test setup, `src/site/main.test.ts:6`).
- Every data-driven `href` is `mailto:`, `tel:`, or a server-issued Wagtail URL (`DashboardPage.tsx:116`, `DoneStep.tsx:66`), and the installed react-dom 19.2.8 blocks `javascript:` URLs.
- `safeNext` refuses off-site `?next=` values (`features/auth/LoginPage.tsx:13-17`).
- `X-CSRFToken` is sent only on unsafe methods, and requests use `credentials: 'same-origin'` (`client.ts:135-139,151-155`). The CSRF cookie is readable in production, as it must be (`backend/caldart/settings/prod.py:65`).
- The client never sends an amount: `CheckoutRequest` names only the plan, the contribution and the provider (`api/types.ts:250-254`; `features/checkout/api.ts:4-5`).
- Stripe confirmation and PayPal capture both go through the server (`checkout/api.ts:37-52`), as PLAN §10 requires.
- Every route guard matches the backend permission class behind it; `system_admin` passes every gate (`nav.ts:64`), as PLAN §5 says:

**Findings.**

- **Finding (medium)**: A failed CSRF bootstrap is cached for the life of the page.
  - **Evidence**:
    - `csrfBootstrap ??= fetch(...).then(() => undefined, () => undefined)` (`src/portal/api/client.ts:77-84`) keeps a resolved promise even when the `GET /auth/csrf` failed, or succeeded without setting the cookie.
    - From then on `readCookie` returns `null` (:137-138), and every POST, PUT, PATCH and DELETE goes out without `X-CSRFToken`. Django answers 403 until the page is reloaded.
    - The same happens if the cookie disappears later in the session.
  - **Suggestion**: Clear `csrfBootstrap` when the fetch fails or the cookie is still missing afterwards. Consider one automatic retry after a CSRF-failure 403.
- **Finding (medium)**: The guards treat an `/auth/me` server error as "signed out".
  - **Evidence**:
    - `fetchMe` rethrows anything that is not a 401 (`auth/useAuth.ts:29-36`), and `useMe` sets `retry: false` (:44).
    - `useAuth` reports `isAuthenticated: user !== null` and `isLoading: query.isPending` (:57-66).
    - So a 5xx or a network error sends a signed-in member to `/login` (`auth/guards.tsx:37-38,51-52`). `AuthState.error` is exposed, but no guard reads it.
    - This contradicts the guard's own comment (`guards.tsx:4-7`).
  - **Suggestion**: When `error` is set and is not a 401, render an error state with a retry, and keep the redirect for real 401s.
- **Finding (medium)**: `CheckoutReturn` never settles in development.
  - **Evidence**:
    - `src/portal/features/checkout/CheckoutReturn.tsx:44-51` uses a `started` ref so its effect runs once, and the effect's cleanup sets `cancelled = true` (:104-107).
    - `<StrictMode>` (`src/portal/main.tsx:14`) runs each effect as setup, cleanup, setup in development, and refs survive that cycle.
    - So the second setup returns at :50, and the only in-flight `settle()` sees `cancelled`: it never calls `onSuccess` (:65-66, :78-79) and never calls `setError` (:96-100).
    - The consequence is that a redirect-based Stripe return (3-D Secure) sits on "Confirming your payment…" under `make run` or `make dev-frontend`, although the server has already confirmed.
    - Production builds are unaffected, because the parent's callback is stable (`useCallback`, `features/join/JoinWizard.tsx:53-60`).
    - The tests pass only because `renderWithProviders` omits StrictMode (`src/test/render.tsx:30-38`).
  - **Suggestion**: Drop the ref guard and make `settle` safe to run twice (the server confirm is idempotent), or express the flow as a query or mutation. React's documentation advises against refs that stop effects from re-running.
- **Finding (low)**: The reminder log is out of reach for account administrators.
  - **Evidence**: `/admin/reminders/log` admits `account_admin` (`reminders/api/views.py:47`; PLAN §6.9 "log also account_admin"), but the portal shows it only inside `/system`, which is `system_admin` only (`features/system/api.ts:58-71`, `routes/system.tsx:9`).
  - **Suggestion**: Decide whether account administrators need a portal view, and record the answer in PLAN §8.
- **Finding (low)**: The client would send the CSRF token to other origins.
  - **Evidence**:
    - `buildUrl` treats any path starting with `http` as absolute (`client.ts:102`), and `request` attaches `X-CSRFToken` to unsafe requests regardless of origin (:135-139).
    - No caller passes an absolute URL today: DRF's `next`/`previous` only disable buttons, for example `features/admin-members/MembersListPage.tsx:173-181`. So this is latent.
  - **Suggestion**: Restrict absolute URLs to the same origin, or remove that branch.
- **Finding (low)**: A GET signs the member out.
  - **Evidence**: `LogoutPage` fires the logout POST from an effect on mount (`features/auth/LogoutPage.tsx:14-18`), so any link to `/portal/logout`, including one on another site, ends the session.
  - **Suggestion**: POST from the Sign-out control (`layout/PortalLayout.tsx:50-52`), or confirm on the page.
- **Finding (low)**: No Content-Security-Policy is set.
