# Backend critique (2026-09-13)

Part 1 is the codebase analysis (python-codebase-analysis skill) and Part 2 is the test-suite critique (critique-test-suite skill).

## Part 1: Codebase analysis

### Codebase analysis: backend/

### Summary

The backend is in good mechanical health: `ruff check` and `ruff format --check` pass, Django's system checks and the missing-migration check are clean, the Sphinx docs build under `-n -W`, `uv audit` finds no known vulnerabilities in 83 locked packages, and the payment paths are carefully built (server-computed totals, provider-side verification, idempotent success under `select_for_update`). The serious problems sit at the authorization and deployment edges. A `user_admin` or `account_admin` can take over a `system_admin` (superuser) account by changing its email and requesting a password reset. The auth throttles can be bypassed with a forged `X-Forwarded-For`, anonymous auth POSTs skip CSRF, and anyone with the URL can download a document attached to a members-only page; probes confirmed all four. Fix those first, then the fail-open production defaults and the per-row membership queries; the remaining layering, duplication, logging and annotation debt can ride along with normal work.

**Scope and method.** All of `backend/` (seven apps, the `caldart` project package, and templates where a finding reached them), plus `deploy/`, `pyproject.toml`, the `Makefile` and CI; the frontend was not reviewed. I ran `ruff check`, `ruff format --check` and, for information only, ruff with extra rule categories. I also ran:

- `manage.py check --fail-level WARNING` and `makemigrations --check --dry-run` under `caldart.settings.test`.
- `manage.py check --deploy` under `caldart.settings.prod`. No production environment file was available, so its result reflects the repository `.env` (see section 10).
- `sphinx-build -n -W` into a scratch directory, and `uv audit`.

An AST pass measured annotation and docstring coverage and mapped the cross-app import graph. Throwaway pytest probes, kept outside the repository and run against a disposable test database, measured query counts and exercised each security finding. Coverage was not measured.

### 1. Structure and layout

- **Finding (Medium)**: The apps import each other in cycles, and the shared abstract base model lives in a domain app. `TimestampedModel` is defined in `members` and imported by `aircraft`, `payments` and `reminders`, while `members` imports back from `aircraft` and `payments` at module level. **Evidence**:
  - `TimestampedModel`: defined at `backend/apps/members/models.py:10`; imported at `backend/apps/aircraft/models.py:11`, `backend/apps/payments/models.py:8` and `backend/apps/reminders/models.py:8`.
  - members → aircraft at `backend/apps/members/api/profile_serializers.py:14` and `backend/apps/members/api/profile_views.py:18`; aircraft → members at `backend/apps/aircraft/models.py:11` and `backend/apps/aircraft/services.py:18`.
  - members → payments at `backend/apps/members/api/profile_serializers.py:24`; payments → members at `backend/apps/payments/services.py:13-14`.
  - The accounts ↔ members and accounts ↔ cms cycles are broken only by inline imports (`backend/apps/accounts/models.py:130`, `backend/apps/accounts/services.py:36,94`).

  **Suggestion**: Move `TimestampedModel` into the project package (for example `caldart/models.py`). Then choose one direction for each pair of apps, and use the inline-import escape hatch that `python.md` §2 allows only where a cycle is unavoidable. The cycles make it difficult to change one app without reading three.
- **Finding (Medium)**: The membership-status rules are implemented twice, and the SQL version lives in the API layer, so domain code imports from `api/`. **Evidence**: The Python implementation is `backend/apps/members/services.py:25-123`. The SQL annotations are `backend/apps/members/api/admin_filters.py:72-164`, and only `backend/tests/test_members_admin_status.py` keeps the two in step. `backend/apps/members/reports.py:20` and `backend/apps/members/api/admin_serializers.py:22` import `membership_payload` from `api/admin_filters.py`. The per-row Python path causes the N+1 queries in section 5. **Suggestion**: Move `membership_annotations`, `member_admin_queryset` and `membership_payload` into `members/services.py` (or a `members/queries.py`) and make them the implementation every list endpoint uses. Keep the Python function for single-user checks only.
- **Finding (Medium)**: Code is copied between apps instead of shared (`python.md` §2, DRY). **Evidence**:
  - Identical `MembershipStatusSerializer` classes at `backend/apps/accounts/api/serializers.py:16-22` and `backend/apps/payments/api/serializers.py:11-17`.
  - Identical `PlanSerializer` classes at `backend/apps/members/api/profile_serializers.py:51-57` and `backend/apps/payments/api/serializers.py:20-26`.
  - The literal `["current", "expired", "none"]` at `backend/apps/accounts/api/serializers.py:19`, `backend/apps/payments/api/serializers.py:14` and `backend/apps/aircraft/api/serializers.py:111,137,141`, plus a fourth spelling as `STATUS_CHOICES` (`backend/apps/members/api/admin_filters.py:65-69`).
  - `send_password_invitation` (`backend/apps/members/api/admin_serializers.py:244-268`) re-implements the reset link from `backend/apps/accounts/services.py:67-84`. It hard-codes the path, skips the `rstrip("/")` on `SITE_URL`, and builds the email body in Python instead of a template.

  **Suggestion**: Prefer one `MembershipState` `TextChoices` in `members/models.py` plus one status serializer and one plan serializer imported where needed. Have the invitation call `accounts.services.build_reset_url` with its own template.
- **Finding (Low)**: Dead code. **Evidence**: These are never referenced outside their own definitions:
  - `CheckoutResponseSerializer` (`backend/apps/payments/api/serializers.py:56`)
  - `IsDartLeader` and `IsWebsiteAdmin` (`backend/apps/accounts/permissions.py:58,61`)
  - `IsSelfOrHasAnyRole` (`backend/apps/accounts/permissions.py:65-81`)
  - `Payment.amount_dollars`, a float view of money (`backend/apps/payments/models.py:95-97`)
  - `MemberProfile.volunteer_interests` (`backend/apps/members/models.py:159-169`)

  **Suggestion**: Delete them (`CLAUDE.md`: delete code a change makes dead).
- **Finding (Low)**: Every module is under the 1000-line limit, but the largest is mostly data. **Evidence**: `seed_content.py` is 835 lines, and lines 52-318 are literal page copy (`backend/apps/cms/management/commands/seed_content.py`). The only function above mccabe complexity 10 is `run` in `backend/apps/aircraft/seed.py:63`, at 12. **Suggestion**: Consider moving the seed copy into a data file beside the command before it reaches the limit.

### 2. Best practices alignment

- **Finding (High)**: Domain logic sits in serializers, and services raise DRF exceptions. This inverts the layering that `python.md` and `security.md` describe, where serializers validate and `services.py` changes state. **Evidence**:
  - `MemberCreateSerializer.create` creates the user, role, profile and invitation email (`backend/apps/members/api/admin_serializers.py:291-312`), duplicating `accounts.services.register_user` (`backend/apps/accounts/services.py:29-46`).
  - `MemberUpdateSerializer.update` (`admin_serializers.py:343-358`) and `AdminUserSerializer.update` (`backend/apps/accounts/api/serializers.py:220-230`) change accounts and roles inline. With two copies of the edit logic, the `system_admin` guard exists in one path and is missing from both edit paths (section 7).
  - `payments/services.py` imports and raises `rest_framework.exceptions.ValidationError` (`backend/apps/payments/services.py:11,26-43`), and so does `payments/reports.py` (`backend/apps/payments/reports.py:20,78,82,98,131`).

  **Suggestion**: Add services that own the rules, such as `accounts.services.update_account(actor, target, ...)` (including who may edit whom) and `members.services.create_member(...)`. Have the serializers call them, and have the services raise domain exceptions that the views translate to 400 responses. Left as is, every new admin path risks another missing guard.
- **Finding (Medium)**: There is almost no logging (`python.md` §2). Only 2 of 92 app modules create a logger: `backend/apps/payments/providers/stripe.py:33` and `backend/apps/payments/providers/paypal.py:35`. **Evidence**: The following write nothing:
  - role changes and deactivations (`backend/apps/accounts/api/serializers.py:220-230`)
  - hard deletes (`backend/apps/members/api/admin_views.py:90-98`)
  - manual membership grants (`admin_views.py:101-119`)
  - backup creation and download (`backend/apps/sysadmin/api/views.py:39-70`)
  - reminder runs

  **Suggestion**: Add `log = logging.getLogger(__name__)` to services and log privileged actions with actor and target ids, and no PII beyond ids (`security.md` §5). As things stand, the takeover in section 7 would leave no trace.
- **Finding (Medium)**: Provider failures are not converted to domain exceptions, so a provider outage becomes a 500 and leaves an orphaned pending payment. **Evidence**:
  - Nothing handles `stripe.StripeError` around `PaymentIntent.create` or `retrieve` (`backend/apps/payments/providers/stripe.py:114-126,141-143`).
  - `httpx` timeouts and connection errors escape `access_token` and `call` (`backend/apps/payments/providers/paypal.py:99-105,128-138`); only `verify_signature` catches them (`:322`).
  - `CheckoutView` catches only `PaymentError` before deleting the pending row (`backend/apps/payments/api/views.py:115-119`).
  - A PayPal capture for the wrong amount raises without logging, which leaves captured money against a pending payment (`paypal.py:235-239`).

  **Suggestion**: Wrap the SDK and HTTP calls, re-raise as `PaymentError` subclasses with `raise ... from` (`python.md` §2), and `log.error` the capture mismatch so someone reconciles it.
- **Finding (Low)**: Several places use a defensive `getattr` on an attribute that always exists, which `python.md` §2 forbids. **Evidence**: Settings defined in `base.py` are read through `getattr(settings, ...)` at `backend/apps/payments/views.py:28`, `backend/apps/payments/providers/paypal.py:304` and `backend/apps/accounts/throttling.py:31`. `getattr(user, "is_superuser" / "has_role" / "has_any_role", ...)` is used on the project's own `User` at `backend/apps/cms/forms.py:21-26`, `backend/apps/cms/context_processors.py:31-36`, `backend/apps/cms/models.py:56-58` and `backend/apps/accounts/permissions.py:27`. **Suggestion**: Reference the attributes directly.
- **Finding (Low)**: 280 lines in 69 non-test, non-migration modules contain non-ASCII characters (em dashes, arrows, `·`, `…`), which `doc_python.md` §2 keeps out of `.py` files. **Evidence**: `grep -P '[^\x00-\x7F]'`. The heaviest file is `backend/apps/cms/management/commands/seed_content.py` (45 lines), and ruff's `RUF001` flags an en dash at `backend/apps/members/models.py:274`. **Suggestion**: Replace them as files are touched. If some user-facing characters are deliberate, amend the rule to allow them in string literals.

### 3. Types and static checks

- **Finding (High)**: Annotation and docstring coverage fall well short of `python.md` §4-5, which require both on every function. **Evidence**: An AST pass over non-test, non-migration code found:
  - 184 of 390 functions (47%) fully annotated, and 155 (39%) with a docstring.
  - `members` lowest, with 26 of 91 annotated and 26 documented.
  - No docstring using a `Parameters:` section.
  - View methods such as `get(self, request)` and serializer `validate_*` and `get_*` methods typically unannotated; `caldart_exception_handler` has neither an annotation nor a docstring (`backend/caldart/exceptions.py:14`).
  - The membership-status payload typed as a bare `dict` alias (`backend/apps/members/services.py:22`) and re-declared as serializers in three apps.
  - Test code 2% annotated (21 of 833 functions).

  This will make it difficult to introduce a type checker later, and many docstrings are too thin to write a black-box test from. **Suggestion**: Annotate and document on touch, as the rule requires for new and modified code. Type the status payload as a `TypedDict` (the RORO rule). Consider ruff's `ANN` and `D` categories (Google convention) app by app once an app is clean.
- **Finding (Low)**: Widening ruff for information surfaces a small, real backlog. **Evidence**:
  - 22 `RUF100` unused `noqa` directives across `backend/`, for rules that are not enabled. Examples: `BLE001` at `backend/apps/payments/providers/stripe.py:182`, `S603` at `backend/apps/sysadmin/services.py:89`, and `N802` at `backend/apps/accounts/permissions.py:44,52`.
  - `N818` on `ProviderNotConfigured` and `MockPaymentsDisabled` (`backend/apps/payments/providers/base.py:14`, `backend/apps/payments/providers/mock.py:13`).
  - An unmarked broad `except Exception` in `health()` (`backend/apps/sysadmin/services.py:235`).
  - `RUF012` fires 175 times in app code, all on idiomatic DRF and Django class attributes.

  **Suggestion**: Consider enabling `RUF` (ignoring `RUF012`) and `N`, as `python.md` §7 contemplates, or delete the dead `noqa` comments.

### 5. Performance and resource use

- **Finding (Medium)**: Two endpoints query membership once per row. `UserSerializer.get_membership` calls `membership_status`, which issues two to three queries per user, and the leader search does the same per result. **Evidence**: `backend/apps/accounts/api/serializers.py:49-50` calls into `backend/apps/members/services.py:29,66,109-115`. The same happens per search result at `backend/apps/aircraft/services.py:79` and per pilot on the aircraft detail card at `:131`. A throwaway probe measured:
  - `GET /admin/users` issued 16 queries for 6 users and 56 for 26, two per row, and `page_size` allows 200.
  - `GET /leader/search` issued 8 queries for 3 matches and 32 for 15.
  - `GET /admin/members`, which uses the SQL annotations, stayed at 4 queries at both sizes.

  **Suggestion**: Serve both endpoints from `member_admin_queryset()` and `membership_payload()` (section 1), and pin the counts with `django_assert_num_queries`.
- **Finding (Medium)**: Stripe calls run with the library defaults, which are longer than every timeout in front of them, and with no idempotency key. stripe 15.6.1 defaults to an 80 s timeout and 2 network retries. **Evidence**:
  - No timeout is passed at `backend/apps/payments/providers/stripe.py:114-126,141-143`.
  - gunicorn has `timeout = 60` (`deploy/gunicorn.conf.py:81`), nginx `proxy_read_timeout 60s` (`deploy/nginx/caldart.conf:127`), and Apache `ProxyTimeout 60` (`deploy/apache/caldart.conf:101`).
  - PayPal, by contrast, sets 20 s (`backend/apps/payments/providers/paypal.py:43`).

  A slow Stripe response can reach the browser as a 504 from the proxy while the request still completes and activates the membership. **Suggestion**: Prefer a `stripe.StripeClient` (or the module settings) with a timeout below the proxy's, and pass an `idempotency_key` derived from the payment id to `PaymentIntent.create`.
- **Finding (Low)**: A module-level mutable token cache is shared between gunicorn's threads without a lock. **Evidence**: `_token_cache` at `backend/apps/payments/providers/paypal.py:78-123`. `worker_class = "sync"` with `threads = 2` makes gunicorn run threaded workers (`deploy/gunicorn.conf.py:60-61`). The race is benign, since two threads may both fetch a token, but it is undocumented. **Suggestion**: Guard it with a `threading.Lock` or move it into Django's cache, and state the thread-safety in the docstring.
- **Finding (Low)**: Backups and restores hold the whole dump in memory. **Evidence**: `capture_output=True` then `result.stdout` at `backend/apps/sysadmin/services.py:156-162`, and `handle.read()` before `psql` at `:180-187`. **Suggestion**: Optional: stream `pg_dump` output into `gzip.open`, and the reverse for restore, once the database grows.

### 7. Security and robustness

- **Finding (Critical)**: A `user_admin` or `account_admin` can take over any `system_admin` (Django superuser) account. Both admin serializers let them rewrite the target's email, and the password-reset flow then mails the link to that address. The code protects `system_admin` only when roles change (`backend/apps/accounts/api/serializers.py:210-218`) and when an account is deleted (`backend/apps/members/api/admin_views.py:95-97`); email and `is_active` edits have no such check. **Evidence**:
  - `AdminUserSerializer.validate_email` and `update` (`backend/apps/accounts/api/serializers.py:196-203,220-230`) sit behind `IsUserAdmin` only (`backend/apps/accounts/api/views.py:199-205`).
  - `MemberUpdateSerializer.validate_email` and `update` (`backend/apps/members/api/admin_serializers.py:334-358`) sit behind `IsAccountAdmin` (`backend/apps/members/api/admin_views.py:48-57,74-88`).
  - Reset by address happens at `backend/apps/accounts/api/views.py:134-150`.
  - A throwaway probe confirmed the chain for both roles: the email PATCH returned 200, and `POST /auth/password/reset` returned 204 with the mail addressed to the new email. The confirm returned 204, and the login returned 200 with roles `['member', 'system_admin']`.
  - The same paths let either role deactivate a `system_admin`.

  This exposes full superuser access, including backup downloads of every member's data, to any compromised or malicious staff account. **Suggestion**: This must be addressed before any real deployment. In one service (section 2), refuse email, `is_active` and password-related changes to an account holding `system_admin` unless the actor holds it too. More generally, refuse them for any account holding a role the actor lacks. Add allow/deny tests for both endpoints, and log the change.
- **Finding (High)**: The login, registration and password-reset throttles can be bypassed, and even without spoofing they count per process. **Evidence**:
  - `AuthScopedThrottle` keys on DRF's `get_ident` (`backend/apps/accounts/throttling.py:33-40`). With `NUM_PROXIES` unset (`backend/caldart/settings/base.py:187-206`), `get_ident` returns the entire `X-Forwarded-For` header (`rest_framework/throttling.py:40`, `''.join(xff.split())`).
  - nginx forwards the client's own header with the real address appended (`deploy/nginx/caldart.conf:115`), and Apache's `mod_proxy` appends in the same way by default.
  - There is no `CACHES` setting, so the counters live in each process's `LocMemCache`. Each of up to 12 gunicorn workers keeps its own, and they reset whenever a worker recycles (`deploy/gunicorn.conf.py:48-51,68`).
  - With the login rate at 2/min, a constant `X-Forwarded-For` got `[400, 400, 429, 429]`. A rotating spoofed value followed by the real address got `[400, 400, 400, 400]`.

  This significantly increases exposure to password guessing and to reset-email spraying. **Suggestion**: Set `REST_FRAMEWORK["NUM_PROXIES"] = 1` in `prod.py`, since both proxies append exactly one address. Configure a shared cache; Django's `DatabaseCache` needs no new dependency. Add a throttle test that sends `X-Forwarded-For`.
- **Finding (Medium)**: Anyone with the URL can download a document attached to a members-only page. The members-only wall covers page rendering only. Wagtail's document view checks collection privacy, not the page's `members_only` flag, and both proxies serve `/media/` straight off disk regardless. **Evidence**:
  - `MembersOnlyMixin.serve` guards only the page (`backend/apps/cms/models.py:105-108`).
  - Document links render `value.document.url` (`backend/templates/cms/blocks/document.html:2`), which is served by `wagtail/documents/views/serve.py:18-34` through `backend/caldart/urls.py:21`.
  - The seeded members-only "Documents and Links" page tells website admins to attach the handbooks, bylaws and forms as documents (`backend/apps/cms/management/commands/seed_content.py:751-770`).
  - Apache has `Alias /media/`, commented "public by design" (`deploy/apache/caldart.conf:73-96`); nginx has `location /media/` (`deploy/nginx/caldart.conf:88-103`).
  - With filesystem storage, an anonymous `GET /documents/2/roster.pdf` returned 200 and the file's bytes.

  **Suggestion**: Recommended: put members-only files in a collection guarded by a `before_serve_document` hook that applies `can_access_members_content`, and deny `/media/documents/` at the proxy so files are reachable only through that view. Alternatively, state that attachments are public and change the seed text.
- **Finding (Medium)**: Anonymous POSTs to the auth endpoints skip CSRF, contrary to the flow in `PLAN.rst` §6 (`PLAN.rst:375-376`). DRF's `SessionAuthentication` enforces CSRF only once a user is signed in, and the default parsers accept form posts. A cross-site form can therefore sign a visitor into an attacker's account (login CSRF) or register accounts from a victim's browser. **Evidence**:
  - DRF's `SessionAuthentication` skips the CSRF check for anonymous requests (`rest_framework/authentication.py:126-128`).
  - The auth views are `AllowAny` (`backend/apps/accounts/api/views.py:52-95,134-165`).
  - There is no `DEFAULT_PARSER_CLASSES` in `backend/caldart/settings/base.py:187-206`.
  - With `enforce_csrf_checks=True` and no token, a multipart login returned 200 and set `sessionid`, and registration returned 201. An authenticated logout without a token returned 403.

  **Suggestion**: Decorate the anonymous auth views with `csrf_protect`; the SPA already sends `X-CSRFToken`. Alternatively, restrict their `parser_classes` to `JSONParser`. Add tests with `enforce_csrf_checks=True`.
- **Finding (Medium)**: One SMTP failure aborts the whole daily reminder scan, and the reminders it did not reach are skipped for good. **Evidence**: `_send_one` runs inside the loop with no error handling (`backend/apps/reminders/services.py:204-213,218-232`). A send error rolls back that log row and propagates, ending the run. Each kind selects `ends_on` equal to one exact date (`:178-184`), and the timer fires once a day (`deploy/systemd/caldart-reminders.timer:17`), so tomorrow's run looks at a different date. **Suggestion**: Recommended: catch and log per-message failures, count them in `ReminderRun`, and select a short window of dates per kind rather than one exact date, relying on the `ReminderLog` constraint to deduplicate.
- **Finding (Medium)**: Hard-deleting a member deletes their payment history, so revenue silently disappears from the payment reports. **Evidence**: `Payment.user` is `on_delete=CASCADE` (`backend/apps/payments/models.py:49-51`), and `DELETE /admin/members/{id}` hard-deletes (`backend/apps/members/api/admin_views.py:90-98`). The summary sums whatever rows remain (`backend/apps/payments/reports.py:123-171`). `PLAN.rst:436` sanctions the hard delete, but not the loss of financial records. **Suggestion**: Prefer `PROTECT` or `SET_NULL` on `Payment.user`, keeping name and email on the payment, or deactivate rather than delete a member with payments.
- **Finding (Low)**: An unbounded `contribution_cents` reaches the database and fails as a 500. **Evidence**: The serializer has `IntegerField(min_value=0)` with no maximum (`backend/apps/payments/api/serializers.py:52`), feeding 32-bit `PositiveIntegerField`s (`backend/apps/payments/models.py:60-62`). A contribution of 3,000,000,000 cents raised an unhandled `DataError: integer out of range`. **Suggestion**: Add a `max_value` so the boundary answers 400 (`security.md` §3).
- **Finding (Low)**: A `<` in a report filter crashes the PDF exports, because filter text is parsed as reportlab markup. Cell values are escaped; the title and subtitle are not. **Evidence**: `backend/caldart/reports.py:155-161` escapes cells, and `:225-227` does not escape the title or subtitle. The subtitles are built from raw query parameters at `backend/apps/members/api/admin_views.py:144-145` and `backend/apps/aircraft/api/views.py:112-123,147`. `search=a<b` raised an unhandled `ValueError: paraparser: syntax error` on both exports, while `R&D` was fine. **Suggestion**: Escape the title and subtitle the same way as the cells.
- **Finding (Low)**: Login reveals that an address belongs to a deactivated account without checking the password. **Evidence**: `backend/apps/accounts/api/views.py:80-89`. Registration already reveals whether an address is registered (`backend/apps/accounts/api/serializers.py:96-102`), so the extra leak is small. **Suggestion**: Consider checking the password before disclosing the deactivated state.
- **Finding (Low)**: `pg_dump` and `psql` receive the database password inside a URL on their command line, where it is visible in the process list. The password is also not URL-quoted, so one containing `@`, `:` or `/` breaks backups. **Evidence**: `backend/apps/sysadmin/services.py:59-67,98-105,156,187`. **Suggestion**: Pass the password through `PGPASSWORD` in the subprocess environment, and quote the user and password with `urllib.parse.quote`.

_Checked, no finding:_

### 6. Parallel execution

- **`conftest.py` writes into the repository.** When no frontend build exists, `pytest_configure` writes `frontend/dist/.vite/manifest.json` and `pytest_unconfigure` deletes it (`conftest.py:86-102`). The module-level flag `_stubbed_manifest` (`:70`) records that it did. Two pytest processes in one checkout, or `pytest-xdist` workers, will race: one deletes the stub while the other runs. This breaks `python_testing.md` §5 ("never write into the repo"). Instead, point `DJANGO_VITE["default"]["manifest_path"]` at a file created under `tmp_path_factory` (a session fixture plus the `settings` override), or at a stub path in `caldart/settings/test.py`.
- **Global Faker state.** `seed_demo` calls `Faker.seed(20260904)` (`accounts/management/commands/seed_demo.py:47-48`), which reseeds the RNG shared by every Faker generator, factory_boy's included. After any of the 10 tests in `test_seed.py`, or `test_cms_seed_content.py:193-198`, runs, every later factory name comes from a seeded stream. Test data therefore depends on execution order. No assertion is known to break today, but order independence is not verified: no plugin randomises order.
- **Process-global caches:**
  - The PayPal token cache is reset by an autouse fixture in `test_payments_paypal.py:31-40` only. Move the reset to `conftest.py` so any future caller is covered.
  - The `app_version` `lru_cache` is handled correctly (`test_sysadmin_api.py:256-273`).
  - The reimported `caldart.settings.prod` module is popped in fixture teardown (`test_sysadmin_settings.py:48-56`).
- **`.env` leaks into the environment.** `caldart/settings/base.py:16` calls `environ.Env.read_env(REPO_ROOT / ".env")`, so every key in the developer's `.env` sits in `os.environ` for the whole session. `test_sysadmin_settings.py` compensates with a hand-kept `UNSET` list (`:30-39`). That list omits `SECURE_HSTS_INCLUDE_SUBDOMAINS` and `SECURE_HSTS_PRELOAD`, which `prod.py:51-52` reads. `test_tls_is_enforced_behind_the_proxy` (`:88`) therefore fails if either is set in `.env` or the shell. CI has no `.env`, so local and CI runs use different settings.
- **Database:** no `transaction=True`, `live_server` or raw connections, so pytest-django's rollback isolates every test. `drop_schema` is always patched out. `BACKUP_DIR` is always under `tmp_path`. Email is the locmem backend, and nothing touches the shared Mailpit container.

### 7. Mocking and dependency isolation

- **External services:** PayPal is mocked with `respx` at the HTTP layer. Stripe is mocked with `monkeypatch` on `stripe.PaymentIntent.create/retrieve` and `stripe.Webhook.construct_event`, using explicit fakes (`FakeIntents`, `test_payments_stripe.py:58-87`). No `MagicMock` is used anywhere, and every double has an explicit return value.
- **Risk of live network calls:**
  - Nothing guards against real HTTP. `test_capture_of_an_order_id_we_did_not_issue_is_refused` (`test_payments_paypal.py:302-307`) has no `respx.mock`. It passes because the guard at `paypal.py:219-220` fires first.
  - If that guard regressed, the code would request an OAuth token from the live sandbox (`paypal.py:99`). The resulting credential error would also become a 400, so the test would stay green while making a real call.
  - Fix: an autouse `respx_mock` fixture (the `respx` plugin is installed; it asserts every request is mocked) for the payment modules.
- **A fake's assertion is swallowed by the code under test.**
  - `stub_construct_event` asserts `secret == "whsec_test"` (`test_payments_stripe.py:308`). The fake runs inside `handle_webhook`'s `except Exception` (`stripe.py:178-184`).
  - A wrong secret therefore surfaces as a 400 "Invalid Stripe signature" rather than an `AssertionError`. Record the secret on the fake and assert after the request instead.
- **Stripe signature verification never runs.**
  - Every webhook test replaces `construct_event`, so the HMAC check, the timestamp tolerance and the missing-header path are all untested.
  - Build a real header in a helper: `t=<ts>,v1=<hex HMAC-SHA256(secret, f"{t}.{payload}")>`. Let the real SDK verify it, and keep the stub only for event-shape tests.
- **Time:**
  - `freezegun` is used in two places (`test_membership_services.py:19-24`, `test_reminders.py:280`). The reminder service tests pass `today=` explicitly, which is equally deterministic.
  - Many other tests read the clock twice: once in a fixture (`today`, `conftest.py:246-250`, or `timezone.localdate()` in a fixture) and again inside the request. Crossing local midnight between the two reads flips the result. Examples:
    - the filename date in `test_members_reports.py:130-137` and `:213-219`
    - all run tests in `test_reminders_api.py:154-237`
    - the `register` fixtures versus the aircraft filters (`test_aircraft_api.py:332-370`)
    - `test_status_truth_table` (`test_leader_api.py:221-268`)

    Provide a conftest fixture that freezes "now" and use it in date-relative API tests.
- **freezegun leaks into pytest's own timer.** With the `frozen` fixture, `--durations` reports about 1,779,879,828 s of setup for each of the 21 tests that use it. freezegun 1.5.5 supports `freezegun.configure(extend_ignore_list=["_pytest.timing"])`; call it once in `conftest.py`.
- **`test_an_expired_token_is_fetched_again`** (`test_payments_paypal.py:104-114`) never lets a token expire. The 30-second floor (`paypal.py:120`) keeps it cached, and the refetch happens only after a manual `reset_token_cache()`. Freeze the clock, move it forward 31 s, and assert a second token request.
- **Environment:** the `settings` fixture is used correctly almost everywhere. `test_accounts_auth.py:237`, `:363`, `:371` and `:379` use `@override_settings` instead; pick one style. The `.env` dependency is covered in §6.
- **Patch targets are correct.**
  - `apps.sysadmin.services._pg_command`, `_run_pg` and `drop_schema` are patched where they are looked up (`services.py:146`, `156`, `176`, `185-187`).
  - `db_reset.drop_schema` and `db_reset.call_command` are patched on the command module that imported them (`db_reset.py:3`, `6`).
  - Broad patches: `monkeypatch.setattr(services.shutil, "which", …)` replaces `shutil.which` process-wide for the test (`test_sysadmin_commands.py:111-132`). `builtins.input` is patched at `:178`, `:187`, `:246` and `:261`. Both are auto-reverted and acceptable.
- **`monkeypatch` versus `mock.patch`:** `monkeypatch` is used throughout, and `unittest.mock` appears nowhere. Consistent.

### 8. Security and input validation
